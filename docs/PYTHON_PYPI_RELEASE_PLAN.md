# FrameViz 0.5.0 PyPI publication plan

This plan keeps one `pip install frameviz` for the Python SDK and the matching native runtime on the published platforms. The first public release would be a genuine Apple Silicon prerelease. The stable release would cover Apple Silicon and Linux x86_64 after both streams are ready. This plan itself authorizes no uploads.

## Publication sequence

| Order | Version and files | Destination and owner actions |
| --- | --- | --- |
| 1. Prepare the account | Proposed project name `frameviz`. Its public PyPI JSON returned HTTP 404 on 2026-11-17. Availability is confirmed by PyPI when establishing the project. | Confirm the owner and whether the project is personal or organization-owned. Complete PyPI account verification and 2FA as applicable. Choose an authorized publisher and confirm the project's file quota once established. |
| 2. Publish a Mac-only release candidate | `frameviz-0.5.0rc1-py3-none-macosx_11_0_arm64.whl`, with an internal native release of `0.5.0-rc.1` and wire protocol `0.5.0`. Build, sign, notarize and staple this exact prerelease App, build the matching wheel, check its size and SHA-256, then install and open it in a clean environment. | After approval, upload that one wheel to the real PyPI project and document the Apple Silicon scope. Test with `python -m pip install 'frameviz==0.5.0rc1'`. The rc1 filename identifies a future artifact. The existing stable wheel remains the 0.5.0 artifact. |
| 3. Request a quota increase if needed | Current Linux candidate size is 114,089,026 bytes. Use the measured size of the planned final Linux wheel in the request. Prepare a 150 MB per-file request for an individual project if the actual limit remains below the final wheel. | After rc1 is publicly downloadable, the approved maintainer can file the size-limit request through PyPI support for **PyPI only**. Supply the project link, size and the reason for bundling the matching native runtime. Wait for confirmation and recheck actual quota before uploading Linux. |
| 4. Finish the independent Linux gates | Re-run platform checks after closing the library-inheritance problem. Use the existing test ZIP for the pending native Ubuntu review. Confirm the result against the final runtime; if the scoped compatibility fix affects the trial, rerun the same smoke on its successor. | A real x86_64 Ubuntu desktop at the already-supported version is enough for this review step. Save native rendering, click and Gizmo logs. Keep the architecture and distro matrix unchanged. |
| 5. Publish both stable wheels | `frameviz-0.5.0-py3-none-macosx_11_0_arm64.whl` and, if the platform review closes, `frameviz-0.5.0-py3-none-manylinux_2_35_x86_64.whl`. Freeze exact hashes and attestations. Existing accepted Mac bytes can be reused if still applicable. | With authorization, make the Linux source delivery and checksum records publicly accessible alongside the matching downloadable wheel, then publish both Python wheels to PyPI. The proposed location for downloadable release assets is a separate public `qqfly/frameviz-dist` release `v0.5.0`, subject to owner approval and repository creation or selection. Confirm `python -m pip install frameviz==0.5.0` and native startup from the files served by PyPI on both target platforms. |

Release preparation must distinguish the package release number from the wire protocol number. The current version sync script ties SDK versions to the numeric protocol; it only accepts plain numeric versions. Do the prerelease version stamping in a separate release build and preserve protocol `0.5.0`. Set the SDK release metadata to `0.5.0rc1`, native Cargo and Tauri release metadata to `0.5.0-rc.1`, and verify Apple bundle version fields, lockfile consistency and the assembler's `--build-info` checks. Carry forward the existing notarization and install records for the unchanged **stable** Mac wheel only.

The proposed stable release page should include the matching Linux wheel, corresponding-source tar archive, SHA-256 list and release notes. Refresh the build receipt if the Linux wheel or AppDir bytes change. The current Ubuntu source set can be reused for unchanged dependencies. The existing private source repository can remain private. On PyPI, publish the platform runtime wheels without a generic SDK-only wheel or sdist for this release so unsupported platforms report no matching distribution. TestPyPI is optional for rehearsals and has a separate quota. The current candidate workflow builds an archive and lacks an upload job; if using Trusted Publishing, approve and configure a specific workflow and protected publish environment first.

PyPI's default file limits are 100 MB for individual projects and 200 MB for organization-owned projects. A size-limit request requires an under-limit release already uploaded to the project; a prerelease qualifies. A pending Trusted Publisher does not reserve the name. [PyPI size limits](https://docs.pypi.org/project-management/storage-limits/) · [Pending Trusted Publishing](https://docs.pypi.org/trusted-publishers/creating-a-project-through-oidc/) · [Python version specification](https://packaging.python.org/en/latest/specifications/version-specifiers/).

## Final release checklist

| State | Item |
| --- | --- |
| Complete | Final Linux local wheel fingerprint, 399-file ELF audit, exact ABI floor, published tag syntax review and concrete Fedora interoperability reproduction. Existing corresponding-source material and hashes. Prior Mac stable notarization, install and startup evidence. |
| Linux technical work | Close host-launch library inheritance and the PEP 600 SONAME rule; complete baseline CPU evidence if needed. Produce a correctly tagged candidate and verify its exact final bytes. [Platform review](PYTHON_LINUX_RELEASE.md#platform-tag-verdict-for-the-frozen-wheel). |
| Device pending | Native Ubuntu x86_64 default desktop, real driver and interaction review using the current package or its relevant successor. [Review instructions](PYTHON_LINUX_NATIVE_REVIEW.md). |
| Account pending | Confirm PyPI owner, account access and quota. If necessary, file and obtain the size-limit increase after the authorized Mac prerelease. |
| Authorization pending | Approve rc1 and the first public upload, the chosen public release asset location, a quota request if needed, and the stable publication. PR merge also requires approval. |
