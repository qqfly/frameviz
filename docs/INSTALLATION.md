# Installation

Use a dedicated development environment and a new, explicit version prefix. Do not overwrite an existing installation to try this unreleased version.

Python source installation:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install ./packages/frameviz-py
```

For an independently built wheel, install its explicit path inside a virtual environment. Offline installation also requires compatible wheels for numpy and websocket-client; a source archive alone is not a complete offline distribution.

C++ source installation:

```sh
cmake -S packages/frameviz-cpp -B .cache/cpp-release \
  -DCMAKE_BUILD_TYPE=Release -DFRAMEVIZ_BUILD_TESTS=OFF \
  -DCMAKE_INSTALL_PREFIX="$PWD/.local/sdk"
cmake --build .cache/cpp-release
cmake --install .cache/cpp-release
```

Consumers use `find_package(frameviz 0.4.0 EXACT CONFIG REQUIRED)`, `frameviz::cpp`, and an explicit `CMAKE_PREFIX_PATH`. The install includes the selected transport library, headers, and license notices. Normal platform dependencies such as system threads and zlib may still be required.

Vue consumers use the three local SDK tarballs generated by `scripts/release/pack-js-sdk-tarballs.sh`. The devkit builder rewrites dependencies to its packaged tarballs. Do not assume registry versions have been published.

The portable installer verifies every manifest-listed file before installing into a prefix that does not exist. Uninstall deletes only unchanged owned files, preserves modified/user files and new empty directories, and does not modify shell profiles or global Python. It stages supplied packages; it does not claim to deploy and register a complete native runtime. Native installer/upgrade behavior must be accepted separately.

One Host owns each state directory. To run multiple Hosts, give every process and its clients a distinct `FRAMEVIZ_HOME` (or explicit discovery path), port, and log directory. Defaults are `~/.local/share/qqfly/frameviz` on macOS/Linux and `%LOCALAPPDATA%/qqfly/FrameViz` on Windows. Legacy state directories and global application names are not searched.

## Linux runtime discovery

`fv.open()` first authenticates a compatible running runtime. Only a missing local service may trigger startup; an incompatible version or a rejected token is reported without launching a replacement. Automatic search uses an explicit `FRAMEVIZ_HOST_PATH`/`FRAMEVIZ_TAURI_APP`, then known installed locations, then compatible source builds. An incompatible live discovery record is preserved.

On Linux without `DISPLAY` or `WAYLAND_DISPLAY`, the standalone executable is preferred. Its installed locations are `/usr/bin/frameviz-server`, `/usr/local/bin/frameviz-server`, and `~/.local/bin/frameviz-server`; arbitrary `PATH` entries remain excluded. With no display, `fv.open()` prints a private browser link and returns the scene context. With a desktop it prefers Tauri and uses a browser if a window cannot be opened. The Viewer address is read after startup, including automatically assigned ports.

Use `fv.open(window_mode=1)` to force the browser path, including on a desktop where Tauri is installed. This existing public parameter is the browser switch; no additional environment variable is needed. Native window opening is bypassed. `window_mode=0` keeps page opening manual. A live runtime started outside the SDK is never stopped by SDK cleanup. If no runtime can be found, the error gives platform-specific runtime installation and source-build guidance; installing a Python wheel alone does not install the native runtime.

Browser links use only the Viewer address advertised for the connected runtime. A missing or mismatched address is an error, rather than a guess at a development server port. Failed view opening releases only the scene/view created by that call. Discovery updates replace a private file atomically; updates and shutdown preserve records owned by another runtime.

Install the FrameViz runtime `.deb` once, then install the Python SDK wheel into each virtual environment that needs it. With a desktop session, the normal entry point is:

```python
import frameviz as fv
viz = fv.open()
viz.add_box()
```

No source checkout or executable-path variable is needed for the standard `.deb` installation. Python checks the known installed executable `/usr/bin/frameviz` before falling back to release/debug binaries in a source tree whose `project_id` and protocol version match this SDK. An installed candidate must be an executable file. SDK startup runs it with `--headless`; opening the scene window uses the existing authenticated control connection, so startup does not display the welcome page.

An explicit `FRAMEVIZ_TAURI_APP` overrides the automatic application search. `frameviz.host.find_host_executable()` also accepts `FRAMEVIZ_HOST_PATH`. Executables with the same name in an arbitrary `PATH` directory are not auto-selected. A missing or non-executable system installation does not prevent the source-build fallback. Wire-protocol compatibility is still checked when connecting.

This describes the discovery contract, not a claim that a particular Ubuntu installation or graphics driver has passed desktop acceptance. Clean Ubuntu 22.04/24.04 `.deb` installation and native-window checks are separate from simulated discovery tests.

Apple Silicon native preview installation, signing status, paired SDKs and source reproduction are documented in [MACOS.md](MACOS.md).

## Standalone Host and browser

The standalone `frameviz-server` binary serves the bundled Viewer without Tauri, a display server, Node.js, or a source checkout at run time. Both WebSocket and HTTP listeners bind only to `127.0.0.1`. Start it in your normal user account:

```sh
./frameviz-server --ws-port 9527 --http-port 8080
```

With no HTTP port argument it chooses a free port. The original positional WebSocket port (`./frameviz-server 9527`) is still accepted. The printed Viewer URL includes the WebSocket port and a temporary authentication token in its `#token=...` fragment. Keep the complete link private; the token is not sent as an HTTP query parameter. The current user's discovery file contains both ports so local Python clients can find them automatically. Startup fails if a requested port cannot be bound or the standalone Host cannot write its discovery file.

For a remote machine, keep the default loopback binding and forward **both** ports:

```sh
ssh -N -L 8080:127.0.0.1:8080 -L 9527:127.0.0.1:9527 user@remote-machine
```

Open the Host's printed URL on your local machine. If you choose different local ports, change the URL's HTTP port and `ws_port` query value to the forwarded local ports. No public network listener is enabled. A link without a valid token cannot read the scene or send commands.

To build the standalone executable from source, prepare its embedded Viewer first:

```sh
pnpm install --frozen-lockfile
node scripts/prepare_web_viewer_dist.mjs
cargo build --locked --release --manifest-path packages/frameviz-server/Cargo.toml
```

The executable is `packages/frameviz-server/target/release/frameviz-server`. Copying that single binary is sufficient for the Viewer assets; normal platform runtime-library requirements still apply. Cross-machine SSH and native Ubuntu desktop acceptance remain separate from a local browser test.


## Ubuntu preview builds

The **Ubuntu runtime preview** workflow builds on Ubuntu 22.04 and 24.04 x86_64 separately. Its private Actions artifacts pair the `.deb`, standalone archive, Python wheel, source commit and SHA-256 checksums. The `.deb` installs both `/usr/bin/frameviz` (desktop) and `/usr/bin/frameviz-server` (headless); the standalone archive includes dependency notices and the relevant MPL source. Build locally on the desired Ubuntu baseline with `scripts/release/build-linux-preview.sh /absolute/new/output` after installing the Tauri build dependencies and workspace packages.

For a preview download, install the `.deb` with `sudo apt install ./frameviz_*.deb`, then install the paired wheel in a virtual environment. For a headless machine, extract the standalone archive and copy `frameviz-server/frameviz-server` to `~/.local/bin/frameviz-server` instead. Keep its notices with the binary when redistributing it. Run the three-line Python example above with no runtime-path configuration.

The workflow verifies dependency installation and automatic SDK startup as a normal user in fresh Ubuntu containers, once with the desktop package and once with only the standalone runtime. This checks packaging and the headless path; a container result does not certify native graphics, a particular GPU, or a second machine. Artifacts are uploaded only after both install checks succeed. Use a 22.04-built artifact for the oldest supported baseline rather than assuming a 24.04 build runs on 22.04. See the [Tauri Debian baseline guidance](https://v2.tauri.app/distribute/debian/).
